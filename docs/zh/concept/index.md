# 核心概念

当你将 MolExp 看作几个职责不同的连接模型，而非一个大框架时，它就容易理解得多。

## 四个层次

| 层次 | 回答的问题 | 核心理念 |
|---|---|---|
| **工作流 Workflow** | 应该发生什么？ | 带有命名数据流的任务图 |
| **工作区 Workspace** | 执行后留下什么？ | 持久化层级：工作区 → 项目 → 实验 → 运行 |
| **智能体 Agent** | LLM 如何驱动这一切？ | 自然语言意图 → 工具调用 → 真实的工作区变更 |
| **资产 Assets** | 数据和输出在哪里？ | 在定义的作用域中有名字的资源，而非无文档的路径 |

这些边界不是学术性的。它们让同一个工作流在本地开发时、从 CLI 运行时、或在集群上运行时保持一致——无需改变工作流本身的含义。

## 关键分离

研究代码变得不可信通常有一个无聊的原因：脚本、参数、日志、输出和"真实"数据集路径全部漂移了。MolExp 通过让每种状态存在于明确的位置来防止这种漂移。工作流保持为可复用图。实验保持为可重复定义。运行保持为一次具体尝试。资产保持为在定义作用域中有名字的资源。

## 阅读本部分

- **[工作流模型](workflow.md)** — 计算模型：任务、依赖、编译、执行。哪些东西*不在*工作流层内。
- **[工作区模型](workspace.md)** — 磁盘层级以及实验（定义）与运行（结果）之间的区别。
- **[智能体](agent.md)** — LLM 对话层：pydantic-ai 外观、两种循环（ChatLoop 和 InteractiveLoop）、会话和事件。
- **[资产与可复现性](assets-and-reproducibility.md)** — 为什么可复用数据需要一等名称和作用域。工作区内的 FAIR 意味着什么。
- **[插件](plugins.md)** — 超越本地执行的可选传输层。
